---
title: Real Caddy resolution
description: Trusted sources, precedence, validation, and recursion protection for real Caddy.
---

Cadder does not embed Caddy. The daemon resolves one trusted Caddy executable when it starts and keeps that path for the daemon lifetime. Project registration never changes the selected executable.

## Precedence

The daemon uses this exact order:

1. An absolute `--real-caddy` daemon-start override.
2. `profiles.<profile>.real_caddy` in the standard per-user `cadder.toml`.
3. `defaults.real_caddy` in the per-user file.
4. `profiles.<profile>.real_caddy` in the administrator-owned system file.
5. `defaults.real_caddy` in the system file.
6. A trusted native executable named `caddy` on `PATH`.

An invalid higher-priority value stops resolution. Cadder does not hide a broken or unsafe configuration by selecting a lower-priority executable.

Project files, registration working directories, files next to Cadder executables, `CADDER_CADDY_REAL_COMMAND`, and shim options do not participate in this chain.

## Path validation

Every configured value is an absolute path. Cadder canonicalizes the executable, requires a regular native executable, and validates its owner and parent directories without changing their permissions.

On Windows, the owner is the runtime account, `SYSTEM`, `Administrators`, or `TrustedInstaller`, according to the source. A less-trusted access-control entry cannot grant write, delete, rename, owner-change, or DACL-change authority. Reparse points and `.bat` or `.cmd` scripts are rejected.

On Linux and macOS, the owner is the runtime account or `root`, according to the source. Group-writable and world-writable components, symbolic links, and files without an executable bit are rejected.

Configuration files pass the same provenance checks and are read through the validated file handle. This binds validation to the bytes Cadder parses.

## PATH and recursion safety

PATH fallback ignores empty and relative entries. It checks only the platform-native `caddy` filename and skips candidates that fail the same trust policy.

Cadder compares operating-system file identity, not just path text, when excluding its shim. A symlink or hardlink to `cadder-caddy` is therefore skipped even when it appears under the name `caddy`.

## Shim behavior

The shim does not accept a real-Caddy selector. `caddy run` attaches only to the running Cadder daemon; it never starts an unmanaged Caddy process as recovery.

Read-only inspection commands such as `caddy version`, `caddy adapt`, and `caddy validate` use the same per-user/system/PATH resolver. Their stderr notice identifies the output as real-Caddy inspection rather than Cadder runtime state.

If resolution fails, the error names the rejected source and the action that restores a trusted setup.
