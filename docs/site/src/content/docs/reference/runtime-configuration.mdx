Cadder keeps runtime state per user. Most users never need to choose the runtime directory manually.

## Runtime Override

Set `CADDER_RUNTIME_DIR` or pass `--runtime-dir` to use a specific directory:

```sh
cadderd --runtime-dir <runtime-dir>
cadder --runtime-dir <runtime-dir> daemon status
caddy --cadder-runtime-dir <runtime-dir> run
```

Use the same runtime override when you start `cadderd`, attach with `cadder`, or run the shim.

## Development Profile

Use the development profile when you need live local Cadder tooling without touching your normal daemon or real Caddy process:

```sh
CADDER_RUNTIME_PROFILE=dev
CADDER_DEV_WORKSPACE=/absolute/path/to/cadder-checkout
CADDER_CADDY_BACKEND=mock
```

The repository `xtask` exposes repeatable helpers:

```sh
cargo xtask dev-env --format powershell
cargo xtask dev-run -- cadder daemon status
```

## Privilege Model

Run `cadderd`, `cadder`, and shim-driven `caddy run` from the normal user account that owns the runtime. If Cadder detects elevated operator execution where the platform exposes that state, it reports a privilege diagnostic through the CLI or web surface.

Read-only inspection, diagnostics, log queries, domain and entrypoint toggles, normal daemon control, and non-IIS workflows do not require administrator privileges. On Windows, IIS handoff requests administrator approval only for the short IIS binding mutation batch.

## Runtime Files

The daemon runtime directory contains ephemeral ownership and process files:

- `cadder.lock`, the daemon ownership lock;
- `daemon.json`, daemon metadata used by clients;
- `effective-caddy.json`, the generated Caddy config applied to the owned real Caddy process.

The IPC socket name is derived from the runtime directory, so separate runtime directories do not collide.

## Durable Storage

Cadder keeps durable profile data in the platform's per-user local-data directory. The file store contains:

- `manifest.json`, which selects the active storage generation;
- `generations/`, with versioned snapshots and JSON Lines transaction and log segments;
- `plans/`, for typed operation plans;
- `secrets/`, for Cadder-owned private key material;
- `recovery/`, for preserved migration and corruption evidence;
- `storage.lock`, which gives one daemon exclusive write ownership.

JSON Lines records are bounded, checksummed, hash-chained, and terminated by LF. Cadder flushes accepted records before storage shutdown completes. General state, history, logs, manifests, and diagnostics contain redacted data rather than secrets.

```sh
cadder history show --limit 50
```

If the store cannot be opened or uses a newer unsupported schema, Cadder reports a storage diagnostic and refuses to modify the file set. It preserves invalid authoritative files for recovery instead of skipping or overwriting them.

## Autostart

Per-user autostart is configured through Cadder:

```sh
cadder autostart status
cadder autostart set disabled
cadder autostart set daemon
```

Supported platforms use native startup mechanisms and remove Cadder daemon startup entries when the mode changes. Unsupported or partially configured platforms return explicit diagnostics.

## Configuration Sources

Cadder supports real Caddy resolution through:

- CLI overrides;
- `cadder.toml` in the project working directory;
- `cadder.toml` next to the Cadder executable;
- environment variables;
- safe `PATH` fallback.

The user-facing TOML format is documented in [cadder.toml](../../user-guide/cadder-toml/).

## Environment Aliases

Cadder accepts both environment variable names below for the same value:

- `CADDER_CADDY_REAL_COMMAND`
- `CADDER_CADDY__REAL_COMMAND`

When both are set, `CADDER_CADDY_REAL_COMMAND` wins. Prefer `cadder.toml` for normal user setups because environment variables are easier to lose across shells and terminals.
