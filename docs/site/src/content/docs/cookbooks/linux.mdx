## Direct use

From the directory that contains Cadder:

```sh
./cadder-caddy run
./cadder tui
```

From any project directory where Cadder is on `PATH`:

```sh
caddy run
cadder tui
```

## cadder.toml

Point Cadder at the real Caddy executable in [cadder.toml](../../user-guide/cadder-toml/). Linux package installs often place Caddy at `/usr/bin/caddy`; manual installs may use another path.

## Optional user PATH setup

Run `cadder setup shim` to create the optional `caddy` alias after a collision check. Keep the real Caddy binary separate and reference its absolute path from the per-user `cadder.toml` when it is not the first trusted `caddy` on `PATH`.

## TUI diagnostics

```sh
cadder tui
```

Use the TUI for daemon state, domains, logs, diagnostics, and activation toggles.

## Isolated runtime directory

Most users do not need to set a runtime directory. For demos, tests, or isolated sessions, use the same override for the daemon, shim, and TUI:

```sh
CADDER_RUNTIME_DIR=/tmp/cadder-demo cadderd
CADDER_RUNTIME_DIR=/tmp/cadder-demo caddy run
CADDER_RUNTIME_DIR=/tmp/cadder-demo cadder tui
```

## Recover from common failures

- If Cadder cannot find real Caddy, check [cadder.toml](../../user-guide/cadder-toml/) first.
- If `caddy run` starts real Caddy instead of Cadder, your shell is finding real Caddy before the Cadder shim.
- If a development profile needs another Caddy installation, set `profiles.dev.real_caddy` in the per-user configuration and start that profile explicitly.
