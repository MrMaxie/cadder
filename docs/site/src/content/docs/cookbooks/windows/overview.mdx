## Direct Use

From the directory that contains Cadder:

```powershell
.\cadderd
.\cadder daemon status
.\cadder tui
.\cadder-caddy run
```

From any project directory where Cadder is on `PATH`:

```powershell
caddy run
cadder daemon status
cadder tui
```

## cadder.toml

Point Cadder at the real Caddy executable in [cadder.toml](../../../user-guide/cadder-toml/). On Windows, literal TOML strings let you write normal backslashes.

## Optional User PATH Setup

Run `cadder setup shim` to create the optional `caddy` alias after a collision check. Keep the real Caddy binary separate and reference its absolute `.exe` path from the per-user `cadder.toml` when it is not the first trusted `caddy.exe` on `PATH`.

## IIS Handoff

Use [Windows IIS handoff](../iis/) when a local IIS site needs to sit behind Cadder's Caddy front door.

Cadder does not require the whole daemon or operator session to run as Administrator for this workflow. Discovery, planning, restore metadata, Caddy config updates, and normal operator actions stay in the user context. Windows asks for administrator approval only when Cadder must mutate IIS bindings.

## Recover From Common Failures

- If Cadder cannot find real Caddy, check [cadder.toml](../../../user-guide/cadder-toml/) first.
- If `caddy run` starts real Caddy instead of Cadder, your shell is finding real Caddy before the Cadder shim.
- If a development profile needs another Caddy installation, set `profiles.dev.real_caddy` in the per-user configuration and start that profile explicitly.
- If an IIS handoff prompt is denied, retry the same action when ready. Cadder leaves non-IIS daemon and operator actions usable.
