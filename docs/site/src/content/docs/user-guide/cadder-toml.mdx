---
title: cadder.toml
description: Configure the real Caddy executable for each Cadder profile.
---

Cadder reads `cadder.toml` from its standard per-user configuration directory. `cadder doctor` reports the exact directory for the current account and platform.

```toml
[defaults]
real_caddy = "/absolute/path/to/caddy"

[profiles.dev]
real_caddy = "/absolute/path/to/a-development-caddy"
```

The profile value overrides `defaults` in the same file. A profile without its own value inherits `defaults`.

For Windows paths, a literal TOML string keeps backslashes readable:

```toml
[defaults]
real_caddy = 'C:\Program Files\Caddy\caddy.exe'
```

`real_caddy` is always an absolute path to a native executable. Cadder rejects relative paths, command names, Windows batch scripts, symbolic-link substitutions, and files or parent directories that a less-trusted account can modify.

## Configuration scope

Cadder uses this order:

1. An absolute `--real-caddy` value supplied when the daemon starts.
2. The selected profile in the per-user configuration.
3. `defaults` in the per-user configuration.
4. The selected profile in the administrator-owned system configuration.
5. `defaults` in the system configuration.
6. A trusted native `caddy` executable on `PATH`.

Project directories, project `cadder.toml` files, environment variables, files next to Cadder binaries, and shim flags never select an executable. A malformed or unsafe higher-priority configuration fails closed instead of silently falling through to another source.

The system configuration is optional. Administrators place it in `%ProgramData%\Cadder\cadder.toml` on Windows, `/etc/cadder/cadder.toml` on Linux, or `/Library/Application Support/Cadder/cadder.toml` on macOS.

See [Real Caddy resolution](../../reference/real-caddy-resolution/) for path validation and shim-recursion behavior.
