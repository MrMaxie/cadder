`cadderctl` is Cadder's non-interactive management CLI. It is designed for shell scripts, CI checks, agents, and operators who want state, diagnostics, and toggles without opening `cadder-tui`.

## Command groups

`cadderctl` currently exposes these top-level groups:

```sh
cadderctl daemon status
cadderctl daemon start
cadderctl daemon shutdown
cadderctl entrypoints list
cadderctl entrypoints disable <registration-id>
cadderctl domains list
cadderctl domains disable <domain> --registration <registration-id>
cadderctl diagnostics show
cadderctl logs show --limit 20 domain <domain> --registration <registration-id>
cadderctl logs tail --limit 20 --poll-interval-ms 750 domain <domain> --registration <registration-id>
cadderctl watch status
```

`cadderctl` stays attach-only by default. Read-only commands, toggles, `watch`, and `logs tail` connect to an already running daemon. Only `cadderctl daemon start` may launch `cadderd`.

## Output modes

`cadderctl` supports three output modes:

- `human` is the default for operators running one-shot commands by hand.
- `json` is for one-shot scripting and machine parsing.
- `jsonl` is for streaming commands such as `watch` and `logs tail`.

Examples:

```sh
cadderctl entrypoints list --output json
cadderctl domains list --output json
cadderctl watch diagnostics --output jsonl
cadderctl logs tail --output jsonl --limit 50 domain app.localhost --registration shim-1
```

## Common scripting patterns

Check whether the daemon is reachable without failing the script when it is stopped:

```sh
cadderctl daemon status --output json
```

List current domains and parse them from JSON:

```sh
cadderctl domains list --output json
```

Disable one managed domain explicitly:

```sh
cadderctl domains disable app.localhost --registration shim-1
```

Fetch recent logs for one domain:

```sh
cadderctl logs show --limit 20 domain app.localhost --registration shim-1 --output json
```

Stream state changes for automation:

```sh
cadderctl watch status --output jsonl
```

## Relation to the TUI

`cadderctl`, `cadder-mcp`, and `cadder-tui` share the same daemon contracts and runtime model.

- Use `cadderctl` when you need predictable output, non-interactive toggles, or agent-friendly polling and watches.
- Use `cadder-mcp` when your agent host already speaks MCP and should call structured local tools instead of shelling out.
- Use `cadder-tui` when you need interactive browsing, navigation, filters, and richer operator context.

Neither tool changes daemon ownership semantics. They are clients of the same per-user backend.

## Future agent integrations

The command structure and output modes are intentionally stable so future Cadder-aware agents can:

- inspect daemon reachability and configuration state;
- enumerate entrypoints and domains;
- request recent logs or stream new ones;
- toggle managed routes explicitly;
- map command failures to stable exit codes and typed machine-readable errors.

That keeps agent workflows aligned with the same backend used by the interactive TUI instead of creating a parallel automation API. If you want a local MCP surface instead of shell-oriented commands, see [cadder-mcp](../cadder-mcp/).
